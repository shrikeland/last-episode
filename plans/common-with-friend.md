# «Что у нас общего» на профиле друга

Карточка: [ideas/010-common-with-friend.md](../ideas/010-common-with-friend.md)

## Goal
На профиле друга над его библиотекой показать два ряда — «Смотрели оба» (с обеими оценками, сначала самые большие расхождения) и «Любимое друга, которого нет у вас» (с кнопкой «Добавить»), без новых таблиц и без лишних последовательных запросов.

## Approach

### Альтернативы (брейншторм)
1. **Всё в `getUserProfile`** — расширить action: грузить там мою библиотеку и проверять дружбу, возвращать готовое сравнение. Минус: `getUserProfile` общий для профиля и `profile/[username]/media/[id]`, он стал бы тяжелее для всех вызовов, а файл могут трогать параллельные задачи.
2. **Клиентский компонент с догрузкой** — `CommonTitles` сам тянет мою библиотеку через action после рендера. Минус: лишний round-trip и мигание блока, нужен `'use client'` там, где он не нужен.
3. **Рекомендовано: отдельный серверный «контекст зрителя» параллельно с профилем.** Новый action `getCompareContext()` в `app/actions/compare.ts` возвращает `{ viewerId, myItems, friendIds }` (две выборки внутри тоже параллельно), страница профиля вызывает его в одном `Promise.all` с `getUserProfile` (правило `async-parallel`). Сравнение — чистая функция `lib/compare.ts`, вёрстка — серверный `CommonTitles.tsx`, в котором клиентские только уже существующие `ScrollRow` и `ProfileAddToLibraryControl`. `getUserProfile`, `ProfileMediaCard`, `ProfileAddToLibraryControl` не трогаем.

### Решения
- **Ключ совпадения — `tmdb_id` + род TMDB, а не `tmdb_id` и не точный `type`.** У TMDB фильмы и сериалы — разные пространства id (фильм 1399 и сериал 1399 — разные тайтлы), поэтому одного `tmdb_id` мало. Точный `type` слишком строгий: `anime`/`animation` вычисляются в `normalizeType` (`lib/tmdb/tmdb.service.ts`) по жанрам и стране на момент добавления и у двух людей могут разойтись для одного тайтла. Поэтому ключ `movie:<id>` для `movie`/`animation` и `tv:<id>` для `tv`/`anime`.
- **«Смотрели оба» — тайтл есть у обоих и ни у кого не в статусе «Хочу посмотреть».** `planned` значит «ещё не смотрел», а ряд называется «Смотрели оба». `dropped`/`on_hold` считаются: человек видел хотя бы часть.
- **Сортировка «Смотрели оба»:** сначала пары, где оценки есть у обоих, по `|моя − его|` по убыванию; при равной разнице — по сумме оценок (сильнее любимое выше), затем по названию. Пары, где оценки нет хотя бы у одного, — в конец, по названию. Ряд показывает первые 30, счётчик — полное число.
- **Порог «любимое» — 8+, запасной вариант — топ-10 по его оценкам.** 8 — уже принятая в продукте граница «высокой оценки»: фильтр библиотеки `rating=8` (`app/(app)/library/page.tsx`, `parseRating`). Если у друга нет ни одной оценки 8+ (строгая шкала), берём его 10 лучших по оценке — «любимое» относительно его же шкалы. Кандидаты — только оценённые и не `planned`. Порог считается по всей его библиотеке, **потом** вычитается моя: иначе «запасной топ» сдвигался бы от содержимого моей библиотеки. Сортировка по его оценке по убыванию, затем по названию; в ряду первые 20.
- **Кто «друг».** Принятая дружба в любую сторону: строка `friendships` со `status = 'accepted'` и `user_id = я` или `friend_id = я` (RLS эту выборку разрешает, см. `20260330100000_friendships_status.sql`). Та же логика, что в `getMyFriends`, но только id — один запрос. На своём профиле (`profile.id === viewerId`), у не-друзей, при скрытой (`is_library_public = false`) или пустой библиотеке друга, а также при пустой моей — блока нет.
- **Пустые состояния.** Нет общих — вместо первого ряда строка «Пока ни одного общего тайтла». У друга нет «любимого» (нет оценок) — второго ряда нет. Любимое есть, но всё уже у меня — строка «Всё любимое @user у вас уже есть».
- **Карточки.** Собственная компактная карточка в `CommonTitles.tsx` (140–152px, как в `ProfileMediaRow`): постер + название ссылкой на `/profile/<username>/media/<id>` (как остальной профиль). В «Смотрели оба» под названием две оценки: `@username ★8` и `Вы ★6` («—», если нет). В «Любимом» — его оценка и `ProfileAddToLibraryControl` (`iconOnly`), как в `ProfileMediaCard`. Акцент через `text-primary`/`border-primary` — CSS-переменная уже переключается режимом Наруто/Саске, поэтому `useTheme()` и `'use client'` не нужны. Эффектов свечения/наклона нет: блок информационный.
- **Лишние запросы.** Моя библиотека (`getMediaItems`) и id друзей грузятся параллельно друг с другом и с `getUserProfile`. Для своего профиля и не-друзей эти два запроса делаются впустую — осознанная цена за отсутствие последовательного ожидания (оба маленькие, по индексу `user_id`).

## Risks / open questions
- **Существующий баг рядом (вне скоупа):** уникальный индекс `media_items_unique_user_tmdb UNIQUE (user_id, tmdb_id)` не учитывает род TMDB — нельзя держать в библиотеке фильм и сериал с одинаковым `tmdb_id`. Если у меня есть фильм N, а в «Любимом» друга сериал N, кнопка «Добавить» получит `already_exists` и просто покажет «В библиотеке». Так же `getLibraryTmdbIds` помечает «уже добавлено» только по `tmdb_id`. Стоит отдельной задачи с миграцией.
- **Большие библиотеки.** Сравнение — O(n+m) на Map, но `getMediaItems` тянет `select('*')` с `overview`. Для круга друзей это ок; если станет тяжело — отдельная выборка узкого набора колонок.
- **Два ряда постеров подряд с рядами библиотеки ниже** — визуально может быть плотно. Если так — сворачивать «Любимое» по умолчанию; в первой версии не делаем.
- **Шкала «8+»** — компромисс. Если окажется, что у друзей 8+ — половина библиотеки, стоит перейти на персональный порог (например верхний квартиль его оценок); функция изолирована, правка в одном месте.
